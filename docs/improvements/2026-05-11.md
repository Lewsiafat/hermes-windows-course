## §B 課程內容缺口

> 上游有但 Lesson 沒涵蓋。學員會看到 wizard 出現「課程沒講」的東西而困惑或亂選。

### B1 — Lesson 1 Step 7 wizard 三個未涵蓋 prompts（**高優先**）

A2 提到的 wizard 完整 9 步裡，**有三步課程完全沒講**：

#### B1a. `Enable sudo support? [y/N]` — 安全性關鍵

- **是什麼**：開了之後 hermes 會把 sudo password 存起來，agent 可不經 user 確認自動跑 `sudo apt install ...` 等。
- **為什麼學員會踩**：看不懂選項、覺得「方便就好」→ 選 Y。
- **真實風險**：
  - hermes 被 compromise（漏洞 / 惡意 plugin / log 外洩）→ 攻擊者拿到 root。
  - 更嚴重：Lesson 2 Telegram 與未來 Lesson 3 LINE 都讓**外部訊息**餵進 LLM。已知 prompt injection 風險：惡意訊息可誘導 LLM 跑 `sudo` 命令。沒開 sudo support 時 OS 會擋；開了就擋不住。
- **建議**：Lesson 1 Step 7 wizard table 加這一行，**強制建議 N**，並附「為什麼要拒絕 — 因為 Lesson 2 / Lesson 3 要把訊息收進來」的因果連結。
- **優先序**：**H**

#### B1b. `Gateway working directory [.]:` — 跟 Lesson 2 強相關

- **是什麼**：wizard 提示「Used by Telegram/Discord/cron sessions. CLI/TUI always uses your launch directory instead.」
- **為什麼學員會踩**：看不懂「working directory」與「launch directory」差別；填了 `.` 不知道是相對於哪。
- **跟 Lesson 2 的關聯**：Lesson 2 Step 5 教把 hermes gateway 包成 systemd service —systemd 的 working directory 跟這個 wizard 設的值直接相關，學員若 Lesson 1 填了 `.` 卻在 Lesson 2 看到 service 從 `/` 啟動會困惑。
- **建議**：Lesson 1 Step 7 wizard table 加這一行，建議填 `.`；Lesson 2 Step 5 systemd service 段落補說明「這個 working dir 就是 Lesson 1 wizard 填的值，會影響 cron / Telegram session 找哪些檔案」。
- **優先序**：**M**（跨 Lesson 議題）

#### B1c. `Setup message platforms? Y/N` → 多選 21 個 platforms

- **是什麼**：wizard 末段問是否設訊息平台，Y 後出多選清單（Telegram、Discord、Slack、Matrix、Mattermost、WhatsApp、Signal、Email、SMS Twilio、DingTalk、Feishu、WeCom、Weixin、BlueBubbles iMessage、QQ Bot、Yuanbao、Google Chat、IRC、**LINE**、Microsoft Teams — 共 21 個）。
- **為什麼學員會踩**：以為設 = 設定好了，但實際只是「啟用 platform，token 等細節要另外設」。
- **建議**：Lesson 1 Step 7 wizard table 加這一行，建議答 N（或 Y 然後跳過勾選），引導到 Lesson 2 才設 Telegram；同時宣告「未來 Lesson 3 LINE 開課時也會在 wizard 這步勾」。
- **優先序**：**M**

### B2 — Lesson 1 對 Provider 選擇的引導不夠（中優先）

### B5 — ngrok 操作手冊速記（為 Lesson 3 預備好的具體命令片段）

> 本次 dogfood 走過的實證流程。Lesson 3 開課時可直接抄用，省搜尋成本。

#### B5.1 申請 ngrok 帳號

1. 開 https://dashboard.ngrok.com/signup
2. 選一種登入方式：
   - **GitHub OAuth** / **Google OAuth**（最快，推薦學員）
   - email + password（需 email 驗證才能進 dashboard）
3. 登入後即進 Dashboard

#### B5.2 取得 authtoken

1. Dashboard sidebar → **"Your Authtoken"**（或左欄「Getting Started」→「Setup & Installation」也會列出）
2. 找到 page 上的 authtoken 字串（看起來像 `2abc...XyZ`，長 base64-ish）
3. 複製到剪貼簿

⚠️ **學員第一個地雷**：authtoken 跟 LINE channel token / OpenRouter key 一樣是 secret。**不要**：
- 貼進公開聊天 / Discord / 直播
- 截圖共享 Dashboard 頁面（authtoken 是明文顯示的）
- commit 進 git（連 `.env` 都別 commit）

#### B5.3 設定 authtoken 到 ngrok agent

```bash
ngrok config add-authtoken <YOUR_AUTHTOKEN>
```

**預期輸出**：`Authtoken saved to configuration file: /home/<user>/.config/ngrok/ngrok.yml`

**驗證**：
```bash
ngrok config check
# 看到 "Valid configuration file at /home/.../ngrok.yml" 即 OK
```

**為什麼這步是 Lesson 3 的核心觀念**：authtoken 不只是「能開 tunnel」，它讓 ngrok free tier 的 agent session 從預設「**短期就斷**」變成「**process 不死就不斷**」。沒設 authtoken 的話 tunnel 撐不過半小時，根本沒辦法用來當 LINE webhook。

#### B5.4 開 tunnel（前景版，dogfood / 測試用）

```bash
ngrok http 8646
```

panel 出來後抓 `Forwarding` 那行的 `https://xxxx-yyyy.ngrok-free.app` URL。

**離開 = tunnel 死**。長期跑要走下面三條路徑之一。

#### B5.5 把 ngrok 服務放到背景管理（依複雜度由低到高）

##### 路徑 A. `tmux` 守住前景視窗（最簡單，最推薦給學員入門）

```bash
# 啟動命名 tmux session
tmux new -s ngrok

# 在 tmux 內跑（看得到 ngrok panel）
ngrok http 8646

# 離開 tmux（agent 繼續跑）：按 Ctrl+B 然後再按 D
# 回來看 panel / 抓 URL：
tmux attach -t ngrok

# 永久關掉（會殺掉 ngrok）：
tmux kill-session -t ngrok
```

**優點**：學員仍能直接看到 ngrok panel；ssh 斷線不影響。  
**缺點**：機器重開後 tmux session 不存在，要手動重 `tmux new ...`。

##### 路徑 B. `nohup` 一次性背景化（最 quick，無 monitor）

```bash
# 啟動：stdout/stderr 都倒進 log file
nohup ngrok http 8646 > ~/.ngrok.log 2>&1 &

# 抓當前 URL（從 log）：
grep -oP 'https://[a-z0-9-]+\.ngrok-free\.app' ~/.ngrok.log | tail -1

# 看狀態：
ps aux | grep '[n]grok'

# 關掉：
pkill -x ngrok
```

**優點**：一行就背景化。  
**缺點**：沒重啟機制；ngrok 自己掛了不會自動拉起來；log 不會 rotate。

##### 路徑 C. systemd user service（最穩定，推薦 VM / production）

建 `~/.config/systemd/user/ngrok-hermes.service`：

```ini
[Unit]
Description=ngrok HTTP tunnel (port 8646) for hermes LINE webhook
After=network-online.target
Wants=network-online.target

[Service]
Type=simple
ExecStart=/usr/local/bin/ngrok http 8646 --log stdout --log-format logfmt
Restart=on-failure
RestartSec=10s
StandardOutput=journal
StandardError=journal

[Install]
WantedBy=default.target
```

啟用 + 監控：

```bash
# 讓 systemd 讀新檔
systemctl --user daemon-reload

# 開機自動 + 立刻啟動
systemctl --user enable --now ngrok-hermes.service

# 看狀態
systemctl --user status ngrok-hermes.service

# 即時看 log
journalctl --user -u ngrok-hermes.service -f

# 從 log 抓當前 URL
journalctl --user -u ngrok-hermes.service --no-pager | \
  grep -oP 'url=https://[a-z0-9-]+\.ngrok-free\.app' | tail -1
```

⚠️ **systemd --user 的雷**：預設情況下 user 一登出，所有 `--user` service 都會 stop。要避免必須開 **lingering**：

```bash
# 一次性開啟（需要 sudo，但只設一次）
sudo loginctl enable-linger $USER

# 確認
loginctl show-user $USER | grep Linger
# 看到 "Linger=yes" 才算 OK
```

開了 lingering 後，user systemd 服務即使 user 登出也會持續跑。

**優點**：機器重開後自動拉起、failure 自動 restart、log 進 journal 統一管理。  
**缺點**：仍然每次 ngrok agent restart 都拿新 random URL — 要解決 URL 變動要再加一個 watcher（路徑 D）。

##### 路徑 D. URL 變動自動同步 watcher（進階；給 24/7 production 想要全自動的人）

ngrok agent restart 時 URL 會變 → 學員手動回去 LINE Console 改 webhook URL 很痛。建一個 systemd-managed watcher：

`~/.local/bin/ngrok-url-watcher.sh`（簡化骨架）：

```bash
#!/bin/bash
# 監聽 ngrok url 變化，自動 patch hermes .env 與重啟 gateway
PREV_URL=""
while true; do
  CURRENT=$(curl -sf http://127.0.0.1:4040/api/tunnels | \
    python3 -c 'import json,sys; d=json.load(sys.stdin); print(d["tunnels"][0]["public_url"])' 2>/dev/null)
  if [ -n "$CURRENT" ] && [ "$CURRENT" != "$PREV_URL" ]; then
    sed -i "s|^LINE_PUBLIC_URL=.*|LINE_PUBLIC_URL=$CURRENT|" ~/.hermes/.env
    systemctl --user restart hermes-gateway.service
    echo "$(date -Iseconds) URL changed: $PREV_URL -> $CURRENT" >> ~/.ngrok-url-watcher.log
    PREV_URL="$CURRENT"
  fi
  sleep 30
done
```

**注意：** LINE Developers Console 的 webhook URL **沒辦法 API 自動改**（LINE 沒開放此 API 給開發者），所以 watcher 只能自動修 hermes 端；LINE 端的 webhook URL 學員仍需手動回 console 改。

→ 真正要 24/7 全自動，必須升級 ngrok 付費版的 **named tunnel / static domain**（拿到固定 URL，永遠不變），此時 watcher 整個拿掉。

**優先序：M**（Lesson 3 開課時的 production-readiness 章節必教，但本次先記著）
